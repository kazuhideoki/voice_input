# ADR-0001: OpenAI 文字起こしを GPT Transcribe と realtime-whisper に限定する

- Status: Accepted
- Date: 2026-07-30

## 背景

このアプリケーションは個人利用を前提としており、過去のモデルとの互換性よりも、
現在利用する高性能モデルへ実装を集中させることを優先する。

従来は OpenAI の複数モデルを実行時に選択でき、その差異を吸収するためにモデル名、
prompt、logprobs、低信頼度箇所などを設定、CLI、IPC、履歴、転写結果へ伝搬していた。
この構成では、利用しない旧モデルを残すだけでも各層の分岐とデータ項目を維持する必要が
あり、文字起こし処理全体の変更コストが高くなる。

移行判断の参考にした日本語音声の比較では、録音済み音声 11 件中 10 件で
`gpt-transcribe` が優先と評価され、平均応答時間と概算料金でも
`gpt-4o-transcribe` を上回った。短ターンの追加比較でも、評価可能な 8 件のうち
`gpt-transcribe` が 4 件で優勢、4 件で同等であり、明確に劣る結果はなかった。
ただし、この比較は人手による正解原稿を用いた WER/CER 評価ではなく、対象音声と
利用条件が異なる場合の優位性までは保証しない。

根拠:
[GPT Transcribe と GPT-4o Transcribe の比較](https://github.com/kazuhideoki/diarize-log/blob/08f0d6f291dfbaab96a547a2f2666275895f8429/docs/survey/gpt-transcribe-vs-gpt-4o-transcribe-20260730/README.md)

## 決定

OpenAI を利用する文字起こし経路を、次の 2 種類に限定する。

- 録音後のファイル文字起こしは `gpt-transcribe` を使用し、既定の経路とする。
- 録音中のリアルタイム文字起こしは `realtime-whisper` として提供し、
  `gpt-realtime-whisper` を使用する。

両経路ともモデルと言語をアプリケーション側で固定し、利用者がモデルを指定する
インターフェースは持たない。日本語入力に用途を限定する。

この境界を明確にするため、次を廃止する。

- GPT-4o Transcribe 系モデルの選択
- 実行時のモデル名指定
- 転写要求に対する任意 prompt の指定
- logprobs と、それを利用した低信頼度箇所の選択
- 旧プロバイダー名や旧モデル名からの互換エイリアスおよびフォールバック

このうち、任意 prompt の廃止はモデル比較の結果から導いたものではない。
`gpt-transcribe` 自体は prompt を利用できるが、モデルごとの任意調整項目を公開
インターフェースとして維持しないという、より広い単純化の判断に含める。

`mlx-qwen3-asr` はローカル文字起こしの選択肢として維持する。これは OpenAI
プロバイダーの限定とは別の境界であり、本決定では廃止しない。

`gpt-live-transcribe` の採否と実装は本決定に含めず、別の判断として扱う。

## 判断理由

### 採用した構成

`gpt-transcribe` を通常経路の既定にし、低遅延用途の `realtime-whisper` と
ローカル用途の `mlx-qwen3-asr` だけを残す。

比較結果から、現在の日本語文字起こし用途で GPT-4o Transcribe 系を維持する積極的な
理由は確認できなかった。一方、ファイル文字起こし、リアルタイム文字起こし、ローカル
文字起こしはそれぞれ異なる利用目的を持つため、この 3 経路は残す価値がある。

モデルをプロバイダーごとに固定すれば、モデル固有機能を共通インターフェースへ伝搬する
必要がなくなる。logprobs と低信頼度箇所の選択は、トークン単位の信頼度を保持し、
辞書置換後の文字位置へ対応付け、入力先で選択する一連の処理を必要とする。残すモデルの
共通要件ではないため、この処理だけを独立機能として維持しない。

任意 prompt は専門用語の認識を補助できる一方、CLI から転写要求まで追加の入力項目を
維持する必要がある。現在の用途では辞書による転写後の表記補正を残し、要求ごとの
prompt 調整は提供しない。認識前の文脈付与を失うことは、実装の単純さと引き換えに
受け入れる制約とする。

互換エイリアスやフォールバックを設けないため、旧プロバイダー名と旧 CLI 引数は
明示的なエラーになる。一方、削除済みの環境設定は読み取られず、IPC の未知フィールドは
既存のデコード方針により無視される。これらはモデル選択として機能せず、固定したモデルへ
暗黙に読み替える互換機能も設けない。

### 比較した選択肢

#### GPT-4o Transcribe 系を残したまま GPT Transcribe を追加する

既存利用者への影響は小さいが、モデル選択とモデル固有機能を引き続き全レイヤーで扱う
必要がある。利用しない互換性のために複雑さが残り、今回の単純化という目的を満たさない
ため採用しない。

#### 既定だけを GPT Transcribe に変更し、旧設定を互換機能として残す

表面的な移行は容易だが、旧設定、分岐、テストを維持する必要がある。また、互換設定が
いつまで有効かという新たな判断を持ち込む。破壊的変更を許容できる個人利用
アプリケーションでは、その移行コストを負う合理性がないため採用しない。

#### OpenAI 経路を GPT Transcribe だけにする

構成はさらに単純になるが、録音中に結果を得るリアルタイム経路まで失う。
ファイル文字起こしとは異なる利用目的があるため、`realtime-whisper` は維持する。

## 結果

### 得られる効果

- OpenAI の通常文字起こしで利用するモデルが一意になる。
- 設定、CLI、IPC、履歴、転写結果からモデル固有の状態を削減できる。
- モデル固有機能を変換・保持する処理が不要になり、変更範囲とテスト対象が小さくなる。
- 旧プロバイダー名と旧 CLI 引数は、別モデルへ読み替えられず誤りとして検出される。

### 受け入れる不利益

- GPT-4o Transcribe 系モデルを選択できなくなる。
- prompt による文脈付与と、logprobs に基づく低信頼度箇所の選択を利用できなくなる。
- 旧 CLI 引数を利用する呼び出し元は動作しない。削除済みの環境設定と旧 IPC
  フィールドは効果を持たず、IPC では指定が無視されたまま処理が成功する場合がある。
- モデルや言語を実行時に切り替える用途には対応しない。
- 比較した短ターンでは `gpt-transcribe` の平均応答時間が 0.703 秒で、
  `gpt-4o-transcribe` の 0.522 秒より約 34.9% 遅かった。入力音声の分布によっては、
  通常文字起こしの待ち時間が増える可能性がある。

これらは、互換性より現在利用する経路の単純さを優先するという本決定の意図した結果で
ある。将来、別モデルや別言語が必要になった場合は、旧来の汎用モデル選択を復元するの
ではなく、具体的な利用目的と必要なインターフェースを改めて判断する。
